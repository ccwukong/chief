## 1. What chief is

A local-first workflow orchestrator that drives agent CLIs as workers: Claude Code, Codex, Cursor, Antigravity and OpenCode today, and any other agent with a usable command-line interface — coding agent or not (a general assistant such as Grok Bot or Hermes) — as an adapter arrives for it.

- **chief owns**: workflow definitions (linear or DAG), run state, a full record of every run, human gates, token accounting, pause/resume/revert (saga).
- **the agent CLI owns**: model access, MCP connectivity (Slack, GitHub, Atlassian Rovo, Google Workspace, Gmail, Miro, Datadog, …), tool execution.
- chief never speaks MCP itself and **holds no MCP configuration**. The servers are the ones the agent CLI is connected to, read from the CLI each time, **in the folder the step runs in** (a CLI's servers differ per folder). By default an agent node may use all of them and the agent decides; a node can be *restricted* to some or to none. If a node names a server the CLI is not connected to, the run stops with that error.

**Who uses it and how.** One person, on their own machine. They draw a workflow in the web UI (or write it as YAML), start it, answer its gates, and read what each step did. Three surfaces, all over the same engine and database:

- **Web UI** (`chief serve`, <http://127.0.0.1:8080>): designer, runs, gates, replay, settings. See "Web UI" in §3.
- **CLI** (`chief …`): every operation of the web UI, plus `--json` output for scripting.
- **Schedules**: cron entries that start runs while `chief serve` is running.

A fourth surface, **a macOS desktop app** (unsigned), is the same web UI in an Electron window over the same server, which the app starts as its own child process (§3 "Desktop application", Phase 10, `docs/desktop.md`).

**What a user must know about steps** (the mistakes seen in real use, 2026-11-10/11):

- A step cannot ask the user anything while it works. Only a gate can; choosing between options needs a gate (`ask`) after the step that produces them.
- A step is given the results of the steps directly before it (see "What a step knows" in §5), not the whole run, unless it is set to `context: all`.
- Steps have no database to read or write. chief stores every step's result and passes it on; a prompt that says "store this in the database" cannot be carried out and does not need to be.
- A run keeps the workflow as it was when the run started; editing the workflow affects new runs only. But while a run is stopped, the model and the prompt of any agent step that has not completed can be changed for that run, then the run resumed (9.42, 9.43).

## 2. Guiding constraints

1. **No hardcoded entry point.** A workflow's first node is whatever the user puts there (Slack, GitHub, Jira, a script…). The bundled Slack example is just an example.
2. **Pure workflow-based.** No skills repo, no plugin system. Every node carries its own prompt.
3. **Everything local, in one SQLite instance.** The single file `chief.db` in chief's home (`~/.chief/state`; see 9.32 and 13.1) holds everything the project persists: configs, workflows, runs, the full message record of every run, gates, usage and web UI drafts. It lives in `~/.chief/state` (§3). There is no second database and no other store. Each feature has its own schema inside that file (see §4).
4. **Don't over-engineer.** One process (engine + HTTP server), one web UI, one `chief` binary, one database. Raw SQL with numbered migrations. No queue, broker, ORM, or microservices.
5. **Token-aware.** Every node's usage is measured, budgeted and visible before and after running.
6. **Reversible.** Each node can declare a compensation. A run can be paused, resumed, cancelled, or reverted node by node in reverse order.
7. **File naming.** All file and directory names are lower-case kebab-case (`dev-plan.md`, `claude-code.md`, `daily-slack.yaml`). Workflow YAML keys and enum values are kebab-case too (`output-schema`, `max-parallel`), so template paths must accept hyphens (`{{inputs.lookback-hours}}`). Code identifiers follow the language convention. SQL tables/columns and the agent's JSON contract fields (`side_effects`, `needs_input`, `how_to_undo`) stay snake_case, since they map one-to-one.

## 3. Architecture

```
 ┌────────────┐   REST + SSE   ┌──────────────────────────────────────┐
 │  Web UI    │◄──────────────►│  chief (single Node process)         │
 │ designer   │                │  ├─ server      (Hono, 127.0.0.1)    │
 │ runs/gates │                │  ├─ engine      scheduler · runners  │
 │ replay     │                │  │               saga · token ledger │
 └────────────┘                │  ├─ adapters    claude-code · codex  │
 ┌────────────┐   same API     │  │    cursor · antigravity · opencode │
 │  chief CLI │◄──────────────►│  └─ store       SQLite (node:sqlite)   │
 └────────────┘                └───────────────┬──────────────────────┘
                                               │ spawn, stream JSON
                                     ┌─────────▼─────────┐
                                     │ claude / codex /  │──► remote MCP servers
                                     │ cursor-agent /    │    (configured in the CLI)
                                     │ agy / opencode    │
                                     └───────────────────┘
```

**Stack (decided 2026-11-20, task 11.1–11.7): TypeScript on Node.** npm workspace with two packages (`packages/chief`: engine + server + CLI, `packages/web`: React + Vite + React Flow), built-in `node:sqlite`, `zod` for schemas, `hono` on `@hono/node-server` for HTTP/SSE, `node --test`, `node:child_process` for the agent CLIs, `esbuild` for the bundle. Rationale: one language front to back, React Flow is the standard drag-and-drop DAG editor, one runtime for the CLI, the server and the desktop app, and no native addon to rebuild.

The stack is Node so that the desktop app (Phase 10) runs the same engine on Electron's own Node: one runtime for the CLI, the server and the app, with no second runtime to ship and sign inside the bundle. The Node runtime is task 11.1–11.7; nothing in §1–§6 depends on it.

**Node points to respect:**

- `@hono/node-server` sits on `node:http`. A long SSE stream needs `requestTimeout = 0` (set in `server/serve.ts`); the default 5-minute request timeout would cut it.
- `node:sqlite` is synchronous (`DatabaseSync`). It has no `db.transaction()` helper and refuses `undefined` / booleans as parameters, so `store/store.ts` holds a small adapter that provides the surface the rest of the file expects (`exec`, `query().get/all`, `run(sql, params)`, `transaction`); that file is the only one that imports `node:sqlite`.
- `process.exit()` does not flush a pipe. Anything that prints and exits at once must wait for the write (the e2e fakes do; see `e2e/fixtures/node-compat.ts`).
- TypeScript runs directly (`node file.ts`) through Node's type stripping, which only erases types: no parameter properties, enums or namespaces. `npm run typecheck` covers the packages, not the e2e folder.

**Local findings (2026-11-10):** Claude Code 2.1.309 and Node 26.12 installed. Codex and cursor-agent not installed, so those adapters are sequenced last. **2026-11-19:** agy 1.5.11 (Antigravity) and opencode 1.18.31 installed; their adapters (7.4, 7.5) were written against the real CLIs. **2026-11-20:** the engine runs on Node 26.12 (`node:sqlite`, type stripping).

### Several runs at once

There is no queue, no worker pool, no supervisor process and no per-workflow worker. `chief serve` is **one** Node process, and every active run is one `async` loop inside it: `POST /api/runs` creates the run and calls `driveRun` without awaiting it (`launch` in `server/app.ts`), so starting ten workflows at once leaves ten loops alive in the same event loop, over the same SQLite handle. A schedule that falls due does the same (`server/scheduler.ts`). `chief run`, `chief resume` and `chief gate answer` drive a run the same way, in the foreground, until the run blocks.

```
chief serve — one process, one event loop, one chief.db
├─ driveRun(run 12) ──► claude agent step ──► exits ──► next step ──► …
├─ driveRun(run 13) ──► claude agent step ──► exits ──► …
└─ driveRun(run 14) ──► waiting_gate   (loop ended; no process is kept for it)
```

**The agent is not a worker.** An agent *step* spawns a fresh CLI process (`claude -p …`, or with `--resume <session>` to continue one), streams its `stream-json` back into `run_messages`, and the process exits. Next step, new process. No CLI process is resident between steps, and none is bound to a workflow or a run.

| Level | What runs at the same time |
|---|---|
| Several runs | All of them, as interleaved loops in the one process; they interleave only at `await` points, almost always while waiting on a child CLI's output |
| Steps of one run | One at a time, in topological order, even when two branches are independent (`pass` in `engine/engine.ts`) |
| A `map` step | `parallel` fans out over as many workers as `max-parallel`; `sequential` does not |
| Child processes | One per running `agent` or `script` step; a run with a parallel `map` has one per item in flight. Nothing else |

**How the loops are kept apart.** All run state is rows keyed by `run_id` in the one database (WAL, `busy_timeout` 5000; the store's methods are synchronous, so a statement never interleaves with another run's). There is no shared in-memory run state. Ownership is what keeps *processes* apart: `driveRun` begins with `claimRun(runId, process.pid)`, refused when another *live process* owns the run (`owner_pid`). That is what stops a `chief run` in a terminal from fighting `chief serve` over the same run; inside one process the pid matches, and the run's own status is what stops a second loop (a terminal or waiting status returns immediately). Within a run, pause and cancel are a flag the driving loop polls; the stop signal goes to the whole process group of that run's child (SIGINT for pause, SIGTERM for cancel, SIGKILL after 5 s, in `util/proc.ts`), so stopping run 12 does not touch run 13's CLI.

**A gate frees the loop.** Reaching a gate sets `waiting_gate` and the loop ends, releasing ownership; answering the gate relaunches the run only if no live process owns it. A run parked on a human costs no process.

**Crash recovery is per run.** On start, a `running` run whose `owner_pid` is gone becomes `interrupted`, and its orphaned children are killed; nothing hands a run to another process automatically. A resume picks the run up from the database (interrupted agent steps continue their session).

**No global cap.** Nothing limits how many runs are driven at once — not a setting, not a semaphore, not a queue. Twenty workflows started together mean twenty concurrent CLI processes competing for CPU and for the CLIs' rate limits. The only throttle is `max-parallel` inside a single `map` step, and a per-run budget that pauses the run at the limit.

### Where chief keeps things

Everything chief persists is in `~/.chief/`, outside any checkout, like the agent CLIs' own folders
(`~/.claude`, `~/.codex`). Cloning, moving or deleting the source tree never touches the workflows or
their record, and nothing a run writes can land inside the repository.

```
~/.chief/
  state/chief.db           the one database (§4)
  state/runs/<run>/<step>/ scratch folders of script steps
  workspace/<workflow>/    the folder each workflow's steps run in (its "working directory")
  workspace/.mcp.json      optional, the user's own: MCP servers for every workflow folder (Claude Code reads it)
```

- **Home** (`state/`): `~/.chief/state`, or `CHIEF_HOME` when that is set (the e2e suite gives every case its own). No code has to know which checkout it belongs to, so there is no "not built from a checkout" failure and no build-time path baked into the bundle.
- **Workspace**: a `workspace` folder next to the home, unless the `workspace-dir` setting names another. A workflow may name its own working directory. The home and the workspace are separate folders because scripts may never read or write the home.
- **The desktop app reads the same folder** (`~/.chief`), so `chief serve` in a terminal and the app window see one set of workflows and runs. Only a test or a deliberately separate install sets `CHIEF_HOME`.
- **It is not in a backup unless `~/.chief` is.** Deleting it deletes every workflow, run and the record with them; `chief doctor` prints the path it is using.
- The folder paths are decided in one file, `packages/chief/src/paths.ts`.

### MCP servers

chief reads the servers; it never adds, edits or removes them.

- **Per folder.** An agent CLI has different servers in different folders (Claude Code: local scope applies to the exact folder it was added in, `.mcp.json` to its folder and those below). chief asks the CLI in the folder a step runs in (the workflow's working directory, or the step's own `cwd`) and remembers the answer per adapter and folder.
- **When.** Before every run, before every resume, when a workflow is validated, and when the designer shows its list (which says which folder it is for). `chief mcp list` shows the current folder's servers, `--workflow <name>` a workflow's.
- **Restricting a step.** `mcp:` absent: every connected server. `mcp: [a, b]`: only those; every other server of that folder is hidden from the step. `mcp: []`: none.
- **Failures.** A server a step names that the CLI lacks or is not connected to stops the run before it starts, with the CLI's reason. A server that fails while a step runs fails the step with the agent's error (`status: mcp_unavailable`). Neither is retried automatically; the user fixes the connection and resumes.

### Desktop application (Electron) — built, Phase 10

**One runtime, one engine.** Electron's main process is Node, and since task 11.1–11.7 the engine is
Node too, so the desktop app runs **the same engine from the same bundle** — there is no Electron build
of the engine, no second implementation and no second runtime to ship. The app is a window over a server
that it starts itself.

```
chief.app (Electron, main process = Node)
├─ spawns  Electron --run-as-node Contents/Resources/server/chief.mjs serve --port 0 --no-open
│    the same dist/chief.mjs the CLI runs      the login shell's environment, stdin a pipe
├─ reads the port from the child's first line of stdout
├─ opens a BrowserWindow on http://127.0.0.1:<port>        the same UI, same REST, same SSE
└─ on quit: SIGTERM the child, wait, then exit             `serve` leaves through process.exit, whose hook kills the agent CLIs
```

Why it works without touching the engine:

- `npm run build` produces one bundle (`dist/chief.mjs`, 1.3 MB) with the web UI embedded and the SQL
  migrations beside it (`scripts/build.ts`). It is JavaScript, so it runs on the Node that Electron
  already contains: `ELECTRON_RUN_AS_NODE=1` turns the app binary into a Node interpreter, and the
  person installing the app needs no Node of their own.
- The server stays its own process. A crash in the server cannot take the window with it, and the
  wrapper can restart it; the alternative, running the engine inside the Electron main process, would
  put the synchronous store on the thread that also handles window events.
- `serve --port 0` prints the port it bound, which is how the e2e helpers find the server; the wrapper
  reads the same line. The port is ephemeral, so it cannot collide with a server run by hand.
- The page and the server share an origin, so the Host/Origin guard in `server/app.ts` passes unchanged
  (`127.0.0.1:<port>`), and SSE keeps working (`requestTimeout = 0`).
- `paths.ts` is not changed and the wrapper sets no `CHIEF_HOME`: the server keeps its state where the CLI
  does, in `~/.chief/{state,workspace}` (decision 14). The wrapper adds two things of its own under the
  same folder: the server's log, `~/.chief/logs/chief.log`, and Electron's profile (cache, cookies),
  `~/.chief/desktop`. Nothing lands in `~/Library/Application Support`. A `CHIEF_HOME` in the
  environment moves all of it together, which is how the e2e cases isolate themselves.
- The window's size and position are a choice about the page, so they are kept like the web UI's other
  such choices, in the database (`draft` key `desktop.window`), not in a file of Electron's.
- Two things the engine needed, both in `server/serve.ts`: `chief serve` leaves through `process.exit`
  on SIGTERM, SIGINT and SIGHUP (Node's default ends a process without running its exit handlers, and the
  handler in `util/proc.ts` is what kills the agent CLIs, which run in their own process groups), and with
  `CHIEF_EXIT_WITH_PARENT=1` it exits when its stdin closes, so a killed app cannot leave a server running
  next to the one the next launch starts.

What the wrapper must do, and why each is not free:

| Concern | Why |
|---|---|
| Spawn, port, health check, restart, quit | The window must not open before the server answers `/api/meta`; quitting must not leave `claude` children behind, and an interrupted run must come back as `interrupted` (the existing `recover`) |
| The login shell's `PATH` | An app opened from Finder gets `/usr/bin:/bin:/usr/sbin:/sbin`, so `which("claude")` finds nothing and every adapter reads as "not installed". The wrapper asks `$SHELL -ilc 'env -0'` once (8 s limit, the app's own environment when the shell cannot answer) and passes the result in the child's environment, which also carries exported keys such as `ANTHROPIC_API_KEY` |
| Where state goes | The wrapper does not choose a home: the server uses `~/.chief/state` like the CLI. It only places its own log (`~/.chief/logs`) and Electron's profile (`~/.chief/desktop`) there, so one folder holds everything and the CLI and the app show the same workflows |
| Links, downloads, navigation | The UI has `target="_blank"` links and a `data:`-URL **Download** for export; in Electron these would open a second window or navigate the app away. They must go to the default browser and to a save dialog, and any other navigation is refused |
| Single instance | Two windows would mean two servers and two schedulers over one database |

**Distribution (decided 2026-11-20): macOS only, unsigned.** No Apple Developer ID, no notarization, no
hardened runtime, so no entitlements work and no nested code to sign: the app contains Electron and
JavaScript, nothing else. The bundle carries only an **ad-hoc signature** (`codesign --sign -`, no
identity), because Apple silicon will not start an app whose Electron signature the Info.plist change
broke. The `.dmg` is therefore not trusted by Apple, so macOS warns the first time the app is opened, and
the README carries the one-time command that clears the quarantine flag:

```sh
xattr -dr com.apple.quarantine /Applications/chief.app
```

Signing and notarizing is backlog B.8; Windows is B.9 (the engine no longer needs a port for it, only a
script sandbox).

**What the desktop app does not change.** `chief serve` remains exactly what it is, so the web version
stays available with no divergence: the same bundle, the same tests, the same database format. Two
consequences the person must know: **schedules fire only while the app is open** (the scheduler lives in
the serving process, §5, and quitting the app ends the server), and the app and a terminal's `chief serve`
show the same workflows and runs, since both use `~/.chief`; run one of them at a time if schedules matter.

### Server log

`chief serve` opens the web UI in the browser once it listens (`--no-open` to skip; 9.63) and prints what it does in its terminal: where its database and workflow folders are, each request that changes something or fails (with the error), runs and steps as they start, finish or fail, gates waiting, writes reported, and each read of the MCP servers (adapter, folder, count, time). What the page asks all the time is left out unless `CHIEF_LOG=debug`. Other commands print no log lines.

### Node types (the building blocks)

| Type | Purpose | Palette entry |
|---|---|---|
| `agent` | Run a CLI agent with the node's prompt, scoped to a set of MCP servers | "Agent" building block. The servers the agent CLI reports are listed beside the palette with their status; a node is given servers by ticking them in its panel |
| `script` | Run a local Python / shell / JavaScript / TypeScript script (`.ts` and `.js` run on Node). JSON in via stdin, JSON out via stdout. Always sandboxed (see below) | "Script" |
| `gate` | Human decision. `ask`: described in plain words, the form is worked out by an agent when the run gets there. Fixed forms without a model call: `select` (pick from a list), `approve` (yes/no/edit), `input` (free text) | "Gate" |
| `map` | Fan out one inner node over a list, `sequential` or `parallel` with `max-parallel` | "Map" |

Not in v1: `switch`/router node. Routing by item kind (code review → GitHub, ADR → Google Docs, ticket → Jira) is done in v1 by giving the inner agent node several MCP servers and telling it in the prompt which to use for which kind. A `switch` node is a cheap addition later if prompt-routing turns out unreliable.

### Agent ↔ chief contract

Each agent node gets its prompt plus a short appended contract:

- **Output**: finish with a single JSON block matching the node's `output-schema`. chief extracts and validates it (one repair retry).
- **Side effects**: list every write performed (`{kind, ref, url, how_to_undo, irreversible}`) in `side_effects`. This feeds the saga ledger.
- **Needs input**: instead of performing a write the node is told to confirm first (e.g. "ask me before sending the PR review"), return `{status: "needs_input", question, proposed}`. chief raises a gate, and on answer resumes the *same CLI session* with the user's reply. This is how "ask me if I wanna change anything or send directly" works without wrapping the interactive TUI.
- **Nothing is lost between steps**: the contract says that only the JSON block is passed on, that it must hold every item in full, and that the agent need not store its result anywhere. Text the agent writes outside the block is kept (`reply`), shown on the run page, and passed to the next step when it is substantial.
- **A server that cannot be used**: when one of the servers the node was given is not connected or keeps failing, the agent finishes with `{status: "mcp_unavailable", server, error}` instead of working around it, and the node fails with that error.
- **Before the contract**, the prompt is followed by the results of earlier steps (see "What a step knows" in §5).

### Script sandbox

Every `script` node runs inside an OS sandbox. There is no off switch; a node can only widen specific permissions.

```yaml
- id: dedupe
  type: script
  run: scripts/dedupe.py
  timeout: 60s
  sandbox:                 # omitted = the defaults
    network: false
    write: []              # extra writable paths; cwd and the scratch dir are always writable
    env: [GITHUB_TOKEN]    # extra env vars to pass through
```

| Aspect | Default |
|---|---|
| Network | Blocked. `network: true` opens it fully (no per-host filtering in v1) |
| File operations | Create, modify, move and delete are allowed in the node's working directory (`cwd`) and in the per-node-run scratch dir `<chief home>/runs/<run>/<node-run>/` (`TMPDIR` points there). Other non-sensitive paths are added with `write:` |
| Reads | Whole disk except secret paths (see protected paths) |
| Protected paths | Never writable and cannot be granted through `write:` (validation rejects overlaps): credentials and secrets (`~/.ssh`, `~/.aws`, `~/.config/gh`, the agent CLIs' folders `~/.claude`, `~/.codex`, `~/.cursor`, `~/.gemini`, `~/.config/opencode`, `~/.local/share/opencode`, keychains; these are also unreadable), chief's own state (its home, `.chief/state`, outside the scratch dir), code-execution hooks (shell startup files, `~/Library/LaunchAgents`, `.git/hooks`, `.git/config`), and everything outside the home directory |
| Environment | `PATH`, `HOME`, `TMPDIR`, `LANG` plus what the node lists. Nothing else is inherited |
| Data | JSON on stdin, JSON on stdout, stderr to `run_events`. Node data is never interpolated into the command line |
| Limits | Timeout, output size cap, whole process group killed on timeout / pause / cancel |

- **Backend, macOS (v1):** `sandbox-exec` with a deny-by-default profile generated per node run. Prototyped from the process layer on 2026-11-10: stdin/stdout, scratch writes, Python and JavaScript/TypeScript scripts work; writes to `$HOME` and `/tmp`, reads of `~/.ssh`, and network are blocked.
- **Windows and Linux:** no backend yet (§12). The `script` node type is disabled there: greyed out in the designer palette, a workflow containing one fails validation at run time with a clear message, and `chief doctor` reports it. Scripts never run unsandboxed.
- **Saga:** a script that only uses the scratch dir has nothing to revert. File changes in `cwd` or `write:` paths are not undone automatically: the script lists them in `side_effects` or the node declares `compensate`, otherwise they show as "manual" on revert. A node with `network: true` must declare a compensation or is flagged "manual".
- **Imported workflows:** nodes that widen the sandbox are listed for one-time approval, keyed on the script's hash.
- **Violations** surface as a normal script error plus a hint naming the sandbox setting that would allow the operation.

### Example workflow definition (the user's daily example)

```yaml
name: daily-slack
agent: claude-code                 # default adapter, node may override
budget: { warn-usd: 2.00, max-usd: 4.00 }
inputs: { lookback-hours: 24 }

nodes:
  - id: plan
    type: agent
    mcp: [slack]
    model: sonnet
    prompt: |
      Summarize what happened in my Slack in the last {{inputs.lookback-hours}} hours.
      Identify action items for me, with kind (code-review | doc | jira | other),
      priority (P0-P3), source URL. Return JSON per output-schema.
    output-schema: { summary: string, items: [{ title, kind, priority, url }] }

  - id: choose
    type: gate
    kind: select
    from: "{{nodes.plan.output.items}}"
    modes: [all, by-priority, one-by-one]

  - id: act
    type: map
    over: "{{nodes.choose.output.selected}}"
    mode: "{{nodes.choose.output.mode}}"      # sequential | parallel
    max-parallel: 3
    node:
      type: agent
      mcp: [github, atlassian, google-drive]
      prompt: |
        Action item: {{item}}.
        code-review → fetch the PR via GitHub, review it, then needs_input before posting.
        doc → draft the ADR/RFC in Google Docs. jira → review/update the ticket.
        Report side_effects.
      compensate:
        prompt: "Undo these side effects where possible: {{output.side_effects}}"

  - id: feedback
    type: gate
    kind: input
    summary: "{{nodes.act.output}}"
    options: [done, restart]        # restart → new run, pending items carried over

edges: [plan -> choose, choose -> act, act -> feedback]
```

A `daily-github.yaml` and `daily-jira.yaml` variant ship alongside to show the entry node is just a node.

## 4. Data model (SQLite)

One database file, one schema per feature. A SQLite file has no named schemas of its own, so the
schema is the first part of every table name: `<schema>__<table>`. A new feature either joins an
existing schema or adds a new one; it never adds a second database.

| Schema | Table | Holds |
|---|---|---|
| `workflow` | `workflow__definitions` | id, name, version, definition_json, base_dir, timestamps |
| | `workflow__schedules` | workflow_id, cron, enabled, inputs_json, last_run_at |
| | `workflow__script_approvals` | workflow_id, node, script_hash: approval of a script node that widens the sandbox, tied to the script's content |
| `run` | `run__runs` | workflow_id + version, a snapshot of the definition it was started with, status (`pending, running, waiting_gate, paused, interrupted, completed, failed, reverting, reverted, cancelled`), inputs_json, totals (tokens, usd), `requested_action` (pause / cancel asked by another process), `owner_pid` |
| | `run__node_runs` | run_id, node_id, attempt, parent_node_run_id + item_index (map children), status, input/output_json, session_id, usage_json, error, compensated_at |
| | `run__gates` | run_id, node_run_id, kind, payload_json, answer_json, status |
| | `run__side_effects` | node_run_id, kind, ref, url, how_to_undo, irreversible, reverted_at |
| | `run__events` | append-only status log (run_id, node_run_id, ts, type, payload); what the UI streams live |
| | `run__messages` | run_id, workflow_id, node_run_id, node_id, ts, direction (`in` to the worker, `out` from it, `user`, `system`), kind, content (full text), meta_json. The complete, ordered record of a run, used for replay |
| `agent` | `agent__mcp_servers` | adapter, folder, name, config_json. A cache of what each agent CLI last reported **for a folder**, refreshed before every run and resume. Not configuration |
| | `agent__mcp_reads` | adapter, folder, read_at: when a folder's servers were last read (0 when the CLI reported none, so it is asked again) |
| `system` | `system__settings` | key, value_json (default adapter, CLI paths, budgets, workspace directory, cached model lists) |
| | `system__migrations` | which numbered migrations have been applied (five so far; 004 made the MCP cache per folder, 005 added the assistant's conversation) |
| `assistant` | `assistant__messages` | ts, role (`user`, `prompt`, `assistant`), content, meta_json (session, model, usage, cost, the run it was asked on, the command line; in the designer the workflow, the change made to it with the canvas before and after, a refused change, the options offered: 9.65). The one conversation of the chat panel (9.64) |
| `draft` | `draft__entries` | key, value_json, seq. Text typed in the web UI that is not saved or sent yet, and the user's choices about the page itself (sidebar collapsed, designer panel width, runs per page, the author's own text kept after Refine) |

The database is also the run's memory: every step's result, every gate answer and the full message record are in it per run. There is no per-run file and no other store. A finished run can be deleted, which removes all of its rows in one transaction.

## 5. Execution semantics

- **Inputs**: a run's inputs are a JSON object laid over the workflow's `inputs` defaults level by level; templates read them at any depth (`{{inputs.params.prlink}}`). A run or a schedule whose referenced inputs have no value is refused before anything starts, naming them (9.48).
- **Scheduler**: ready set = nodes whose predecessors completed. Top level runs in dependency order; only `map` fans out.
- **Several runs at once**: one process drives them all as interleaved loops, each run's steps one at a time and each step its own short-lived CLI process; there is no queue and no global cap (§3 "Several runs at once").
- **Pause**: stop dispatching; in-flight CLI processes get SIGINT and the node is marked `interrupted` with its `session_id` kept so it can be resumed in place.
- **What a step knows** (`context`): by default (`previous`) an agent step is given, after its prompt, the stored results of the steps directly before it, as JSON, unless the prompt already inserts them with a template. A gate that carries only a decision or a comment (an `input` gate, an `approve` gate without a value) does not hide what it was about: the step after it is also given the results of the steps before that gate, labelled as such. A gate that passes data on itself (`select`, `ask`, `approve` with a value) stands for it. `all` gives every earlier step, `none` nothing. Inside a map the step is given its item. Results above the output size limit are cut with a marker. Each agent call is its own session: steps share stored results, not a conversation.
- **A run follows the workflow it started with**: the definition is copied into the run. Later edits to the workflow apply to new runs. One exception, on the run page: resuming a stopped run takes the workflow's current prompt and model for the steps it has not completed, unless the user keeps the run's own (9.58). Inside a run, an agent step's **model** and **prompt** can be changed while the run is stopped (failed, paused, interrupted, waiting at a gate), for a step that has not completed, including one that has not started. Each change is written to the run's record as `run_step_changed` with the old and new value, and a new prompt is validated like a workflow edit. On resume a failed step gets a new attempt; an interrupted step continues its session with a new model but starts again with a new prompt (its interrupted attempt is closed as cancelled); a step waiting for the answer to its own question has the question withdrawn and starts again when its prompt changes, and the run is paused so that Resume runs it (9.44). When the workflow has changed since the run started, the editor offers the newer version's prompt and model. This is the way out of a context-window error, or a prompt that turned out wrong, without running the whole workflow again.
- **Run again**: a new run of the same workflow as it is now, with the inputs and the budget of an earlier run. Nothing is carried over from the earlier run's steps (9.61).
- **Resume**: recompute the ready set from the DB. Interrupted agent nodes resume their session rather than restarting. Resuming a failed run gives its failed steps a new attempt and keeps completed ones. The MCP servers are read again first.
- **Crash recovery**: on start, any `running` run whose owner process is gone becomes `interrupted` and is listed for the user to resume. A run owned by the very process that is starting counts as gone too: the dev server (`node --watch`) reloads inside the same process when its source changes, which stops the step in progress.
- **Delete**: a finished run (completed, failed, cancelled, reverted) can be deleted with its whole record. An active run cannot; it is cancelled first.
- **Retries**: only for infrastructure failures (CLI crashed, no JSON output). Never auto-retry a node that reported side effects.
- **Revert (saga)**: walk completed `node_runs` in reverse order, run each compensation (agent prompt in a fresh session with the side-effect ledger, or a script). Nodes with side effects but no compensation, and effects marked `irreversible`, are reported as "manual". Read-only nodes have nothing to compensate.
- **Restart**: the feedback gate's `restart` creates a new run with unfinished items injected as `inputs.carry-over`. No cycles in the DAG.
- **Any process can drive a run** (as built): all run state is in the database, so `chief run`, `chief gate answer`, `chief resume` and `chief serve` each advance a run until it blocks. One process owns a run at a time; a pause or cancel from another process is a flag the owner polls.

## 6. Token awareness

- Usage captured per node from the CLI's JSON output (tokens in/out, cache read/write, cost, model) into `node_runs.usage_json`; rolled up to the run.
- Budgets at workflow level with per-run override (and a `default-budget` setting): soft `warn-usd` emits an event, hard `max-usd` pauses the run with a gate ("continue / stop"). Continuing raises the limit to one step above what is already spent.
- Claude Code and OpenCode report cost. Codex and Antigravity report tokens only and Cursor nothing, so USD budgets do not limit those adapters.
- Context hygiene: downstream prompts receive node *outputs*, never transcripts (the transcripts are recorded for replay, not fed forward). Outputs above a size limit are truncated with a warning (optional summarization by a cheap model later).
- Prompt size estimate shown in the designer and in `chief runs show`. It is the size of the prompt only. It does not predict cost: in real runs a 165-token prompt that reads Slack used 240,000 input tokens (about $0.50), nearly all of it tool results. A cost estimate from the workflow's past runs is proposed (§12, B.3).
- Per-node `model` override so cheap nodes stay cheap.
- Refine (rewriting a prompt in the designer) is a separate, small agent call outside any run; its cost is shown next to the result and is not counted in a run's totals.

Consequence: nothing is in a backup unless `~/.chief` is, and deleting it deletes every workflow and run.

15. **The web and desktop experience comes first; the CLI is frozen** (2026-11-20, Phase 15). The user: *"i don't feel we should rush to deliver CLI commands, as we should focus on shipping great UX for web and desktop apps first."* So a capability is finished when it works without a terminal: an HTTP endpoint **and** a screen for it, tested through the UI. The CLI stays exactly what it is — a scripting surface, a recovery path for a broken UI, and how `chief serve` starts — and gains no new commands except the ones the UI itself needs. Consequences: (a) the two capabilities the audit found UI-less are Phase 15 tasks (schedules, removing a workflow); (b) closing the desktop window keeps chief running, because schedules that only fire while a window is open are not a feature (15.3, decided by the user 2026-11-20: *"the app still runs in background until the user quit the app completely"*); (c) the README leads with the app (15.4); (d) a case keeps every future command honest (15.5), so this does not depend on remembering it.

## 10. Out of scope for v1

Skills repos, cloud sync, multi-user, chief acting as an MCP client itself or configuring MCP servers, a backlog, auth, `switch`/router node, a native mobile app (the web UI is responsive), Windows support, per-host network filtering for scripts, changing a step while it is executing, a per-run file store beside the database. (Changing an unfinished step's model or prompt while the run is stopped is in scope: 9.42, 9.43.) Phase 10 adds a desktop front end for macOS only; a signed and notarized build (B.8) and a Windows build (B.9) stay out of scope.

## 11. Risks

| Risk | Mitigation |
|---|---|
| The process layer (signals, process groups, line-by-line streaming) is hand-written over `node:child_process`, and a stopped run could leave an agent CLI alive | Every case that starts, pauses, cancels or kills a run passes on Node (2026-11-20 full suite: 296 passed); `killOrphan` still pairs a pid with its `ps` start time, and children run in their own process group |
| CLI flags and JSON formats drift between versions | Spike per adapter (0.1–0.3; for Antigravity and OpenCode the contract pages under `docs/adapters/`), `chief doctor` checks minimum versions |
| Agent ignores "ask before writing" | Planning nodes get no write tools; write tools only after a gate; side-effect ledger as the safety net |
| Some effects cannot be undone (sent Slack message, email) | `irreversible` flag, gate before such actions by default, listed as manual on revert |
| `sandbox-exec` is deprecated by Apple and could stop working | `chief doctor` probes it; the script node type is disabled when the probe fails; backend is behind one interface so it can be swapped |
| Fan-out burns tokens | `max-parallel` default 3, hard budget pauses the run |
| Prompt-based routing by item kind is flaky | Add a `switch` node if 5.4 shows it |
| A prompt asks for something a step cannot do (ask the user, use a database, use a result it was not given) and the user finds out only from an odd result | Seen three times in real runs. Partly addressed: a comment-only gate no longer hides the step before it (9.40), the README lists the three traps. Prompt checks and "what this step had to work with" are proposed (B.4) |
| An agent CLI's MCP servers depend on the folder, so a server the user "has" is missing in a workflow's folder | chief reads the servers per folder and the designer names the folder (9.34). Setting a server up for every workflow folder is the user's step in the CLI; an automatic route is undecided (B.6) |
| The dev server reloads on a source change and stops the step in progress | Such a run is now marked interrupted and can be resumed (9.39). `chief serve` without `--watch` does not reload |
| A token for an MCP server sits in a file under `.chief/` | `.chief/` is git-ignored; chief never writes such a file itself |
| A page being edited by an agent is too large for the agent to read without file tools (seen with a 204,000-character Confluence page) | The step needs read-only built-in tools, and a prompt that names the section to change; mark such steps `irreversible` so they ask first |
| The desktop app ships unsigned, so macOS refuses the first open with a warning that looks like the app is broken | The README carries one command that clears it (`xattr -dr com.apple.quarantine /Applications/chief.app`, 10.5), and the download page says why. Signing and notarizing (B.8) removes the step once there is a Developer ID |
| The desktop app depends on a PATH and an environment that Finder does not provide, so every agent CLI reads as not installed | The wrapper reads the login shell's environment once and passes it to the sidecar (10.3), and a case compares `doctor` in the app with `doctor` in a terminal |
